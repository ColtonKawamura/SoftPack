# T-1m55: snapshots and movies

*Up:* [Design decisions](index.md)

**Question.** `Snapshots` had no path, `Movie` had its own `every`, and "pack() writes no
file" was contradicted by three options.

**Choice.** Frames stay out of the `Packing`; a snapshot is a matrix of positions stored
at intervals and written by `write_packing`, and a movie is rendered at run time into a
temporary directory and encoded at the end. The wording is fixed: `pack()` writes no file
by default; `snapshot` data is written by `write_packing`, while `movie` and `restart_file`
write during the run.

**Why we did not adopt the card's option 1.** That option has the movie render from the
snapshots, which stores one position matrix per frame and renders at the end. It is
elegant for positions, but the rotation markers need the particle rotations at each frame,
and snapshots do not carry them; rendering at run time is also cheaper in memory (1.3 ms
per frame, no stored frames) and survives a killed job with the frames already on disk.
The card's own goal — one obvious place for frames — is met by saying plainly where each
one lives.

**Status.** In code; a deviation from the recommendation, recorded here because the
reason matters more than the option number.
